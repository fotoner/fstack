# proto

정해지지 않은 결정 하나를 버릴 코드로 가린다. 산출물은 결정과 그 근거이고, 코드는 버린다.

이 스킬 안에서는 시험·최소 변경·코드 품질을 요구하지 않는다. 금지(H1·H2), 취향 규칙(C13·C22), 증거 등급(C15)은 그대로다.

## 쓰지 않는 경우

- 남길 코드(시험을 갖춘 스파이크, 제품 저장소 브랜치의 PoC)와 본 구현: `build`.
- 그림 도구로 만드는 시안(포스터, 배너, 목업 이미지).
- 이미 있는 코드를 돌려 보는 확인: `verify`.

## 결정의 종류

| 결정 | 만드는 것 | 후보 수 | 관찰 |
|---|---|---|---|
| 화면(레이아웃, 상호작용, 밀도) | 단일 HTML이나 가장 가벼운 수단. 후보를 한 페이지에서 전환하고 이름표를 붙인다 | 둘 이상 | 후보별 캡처, 직접 조작 |
| 접근 선택(라이브러리 A와 B) | 가장 작은 스크립트 | 둘 이상 | 실행 출력, 로그 |
| 가능 여부(API가 실제로 되는지) | 가장 작은 스크립트 | 실험 하나 | 실행 출력, 통과·실패 |
| 성능·시간(기준을 넘는지) | 측정 스크립트 | 실험 하나 | 측정값(조건과 반복 횟수 포함, C14) |

## 절차

1. **결정할 것을 한 줄로 적는다.** 무엇을 보면 어느 쪽을 고르는지도 함께 적는다. 결정할 것이 없으면 그 사실과 `build`로 갈지를 한 줄로 적고 추천 해석으로 진행한다(C6).
2. **격리해서 만든다**: 기본 위치는 저장소 밖 임시 폴더다(화면 시안도 같다). 제품 코드 위에서 봐야 하면 `git worktree add --detach`로 저장소 밖에 버릴 worktree를 만들고 브랜치는 만들지 않는다. worktree에는 커밋된 것만 들어가므로, 필요한 미커밋 변경은 본 체크아웃을 그대로 둔 채 그 부분만 옮긴다. 제품 본 체크아웃의 파일과 잠금 파일은 바꾸지 않는다. H1·H2는 그대로다(fixture, 별도 포트, 내가 띄운 PID).
3. **후보를 만든다**: 수와 관찰 방법은 위 표를 따른다. 색이나 문구만 다른 변형은 후보로 세지 않고, 사용자가 후보를 지정했으면 그 후보를 만든다. 가능 여부나 성능을 확인하는 결정이면 통과할 때와 실패할 때 무엇을 할지 먼저 적는다.
4. **직접 보고 보고한다**: 직접 띄우고 돌려서 본 근거와 장단점을 적고, 비교면 추천 1개를, 가능 여부면 통과·실패를 낸다. 사용자가 봐야 하는 화면은 보이게 전달한다. 프로토타입 통과는 제품의 완료가 아니다.
5. **결정을 옮긴다**: 사용자가 고르면 스펙의 열린 질문을 지우고 요구로 옮긴다(`spec`). 스펙이 없으면 결정 한 줄을 이슈나 대화에 남긴다.
6. **정리한다**: 띄운 서버는 캡처 뒤에 끈다(사용자가 직접 조작할 때만 둔다). 버릴 worktree는 결정을 옮긴 뒤 경로를 보이고 직접 지운다. 결정이 이번 세션에 나지 않으면 worktree 경로를 보고와 `wrap`의 이월 항목에 남긴다. 임시 폴더는 `wrap`의 정리 목록에 넣는다. 프로토타입 코드는 머지하지 않고, 본 구현은 `build` 규칙으로 처음부터 한다.

프로토타입이 본 구현만큼 커지면 멈추고 보고한다.

```markdown
|---|---|---|---|

정할 것: <사용자가 고를 것 / 없음>
```
