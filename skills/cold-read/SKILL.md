# cold-read

문서는 사용자가 AI와 주고받은 대화 속에서 만들어진다. 그 대화에서 생긴 이름, 번호, 결정, 이유가 설명 없이 문서에 남는다. 작성자와 AI는 그 맥락을 알아서 빠진 것을 보지 못한다. 다른 사람은 문서만 받는다. 이 스킬은 맥락을 전혀 모르는 독자에게 문서만 읽혀서, 문서 하나로 완결되고 처음 읽어도 쉽게 읽히게 만든다.

찾는 것은 세 가지다.

- 암묵지: AI와의 대화에서 붙인 이름("1안", "시안 6")과 번호("Q1", "요청 1번"), 앞선 대화를 가리키는 말("앞서 정한", "지난번"), 이 문서로 완결되지 않는 외부 참조(링크나 다른 문서를 열어야 뜻이 통하는 곳), 설명 없는 약어, 이유가 대화에만 있는 결정.
- 맥락 없이 파악하기 힘든 곳: 다시 읽어야 했던 문장, 요청이나 결정에서 빈 칸(누가, 무엇을, 언제까지, 무엇을 기준으로, 어떻게 확인하는지).
- 오해할 수 있는 문장: 두 가지로 읽히고, 읽기에 따라 할 일이나 결정이 달라지는 문장.

## 쓰지 않는 경우

- 사실·논리 검토는 `council`, 문장 다듬기는 `polish`가 맡는다. cold-read를 마친 판을 `polish`로 넘긴다.
- 작성자 본인만 읽는 메모, 핸드오프, 코드, 번역.

## 독자

- `~/dev/fstack/local/routing.md` 1절의 `cold-reader`. 부르는 경로와 샌드박스 프로젝트는 같은 파일 3절에 있다. 부를 경로가 없으면 다른 모델로 바꾸지 않는다. 보고 첫머리에 cold-read 미실행과 이유를 적고, 아래 `scan` 결과로만 판정한다.
- 문서를 다른 호스트로 보내도 되는지는 ROUTING 3절로 확인한다. 회사 문서를 개인 호스트로 보내야 하면 그때마다 사용자에게 묻는다.

## 격리

독자는 문서만 본다.

1. 지시문을 손으로 쓰지 않는다. `python3 -I ~/dev/fstack/skills/cold-read/scripts/cold_read.py brief read <판>`의 출력을 그대로 `delegate_task`의 task로 보낸다. 글의 종류, 독자, 목적, 용어 풀이, 작성자 이름, 이전 라운드의 지적을 더하지 않는다.
2. 독자는 빈 샌드박스 프로젝트에서 돈다. 라운드마다 새 `delegate_task`(`role: "review"`, `mode: "async"`, 새 `clientRequestId`)를 쓰고 이전 스레드에 잇지 않는다.
3. 끝난 뒤 독자 스레드를 `t3_thread_read`(`view: "activity"`)로 읽는다. 작업 공간 준비 항목을 빼고 사용자 메시지, 추론, 답, 체크포인트 밖의 항목이 있으면 도구를 쓴 것이다. 그 결과는 버리고 새 독자를 부른다. 두 번 이어지면 미실행으로 보고한다.
4. 독자가 문서 밖 단서로 메운 뜻은 모르는 것으로 센다.

## 1. 준비

- 문서를 파일에서 다시 읽고 판을 보존한다(`r0`).
- `cold_read.py scan <판>`으로 대화의 흔적, 외부 참조, 약어, 모호 신호를 뽑는다. 판정에만 쓰고 독자에게 보내지 않는다.
- 그대로 둘 말을 정한다. 실제 독자가 모두 아는 회사, 서비스, 제품 이름 정도다. 이 목록도 독자에게 보내지 않는다.
- 답안 시험을 준비한다. 문서의 핵심(목적, 요청, 기한, 결정, 범위, 담당)을 묻는 질문 5~8개를 질문 파일에 쓰고, 의도한 답은 따로 적는다. 질문에는 문서에 이미 있는 말만 쓴다. 규칙은 `templates/answer-test.md`에 있다.

## 2. 라운드

- 새 독자 둘을 동시에 부른다. 하나는 자유 읽기(`brief read <판>`), 하나는 답안 시험(`brief answer <판> --questions <질문 파일>`)이다. 자유 읽기를 따로 두는 이유는 질문이 이끌지 않은 읽기를 얻기 위해서다.
- 독자가 도는 동안 글을 고치지 않는다. 완료 알림을 기다리고 폴링하지 않는다. 타임아웃, 오류, 무응답은 통과가 아니다.
- 다음 라운드의 독자도 새로 부른다. 독자는 이전 지적이나 원장을 받지 않는다. 이전 지적이 풀렸는지는 오케스트레이터가 원장으로 대조한다. 답안 시험의 질문은 라운드마다 같게 둔다.

## 3. 판정과 반영

- 가장 먼저 고칠 것(blocker): 독자가 쓴 "원하는 것"이나 요약이 의도와 다른 것, 답안 시험의 틀린 답, 두 가지로 읽힌 답.
- 오해할 수 있는 문장은 한 가지로만 읽히게 고친다. 빈 칸을 채우거나 읽기를 가르는 말을 바꾼다. 채울 사실을 작성자도 모르면 지어내지 않고 사용자에게 묻는다.
- 나머지 지적은 문서 안에서 해결하고, 지적마다 아래 가운데 하나로 원장에 적는다.
  - 풀어 씀: 대화에서 붙인 이름과 번호는 풀이를 덧붙이지 않고 그 자리를 뜻으로 바꿔 쓴다. 예: "1안" → "공지 기간을 7일로 두는 안".
  - 지움: 독자가 몰라도 되는 참조. 작업 경위, 대화 속 번호, 판 이름.
  - 옮겨 적음: 외부 참조는 링크를 남기고, 읽는 데 필요한 내용을 문서 안에 한두 문장으로 적는다.
  - 이유 넣음: 결정의 이유가 대화에만 있으면 한 문장으로 넣는다.
  - 그대로 둠: 1단계에서 정한 그대로 둘 말.
  - 시험 산물: 실제 독자에게는 문제가 되지 않는 것. 예: 노션이 함께 보여 주는 화면 요소.
- 다시 읽어야 했던 문장은 원인이 빠진 맥락이면 여기서 고치고, 문장 자체면 `polish`에 넘긴다.
- 풀어 쓰기와 지우기를 덧붙이기보다 먼저 한다. 반영한 뒤 `cold_read.py grow <r0> <지금 판>`으로 글자 수를 본다. 20% 넘게 늘면 반영을 멈추고 사용자에게 보인다.

## 예산

- 기본 2라운드, 최대 3라운드. 1라운드의 판정이 NEEDS-REVISION이거나 답안 시험에 틀린 답이 있으면 2라운드를 연다.
- 3라운드는 blocker가 남았거나 사용자가 요청할 때만 연다.
- 합의: 자유 읽기 CLEAR, 답안 시험이 모두 맞음(의도한 "문서에 없음"은 맞음으로 친다), 열린 blocker 없음.
- 교착: 같은 지적이 두 라운드 이어지거나 예산이 끝남. 남은 지적과 오케스트레이터의 판단을 2~3줄씩 보이고 사용자가 정한다. 예산 소진은 합의가 아니다.

## 4. 보고

라운드 수, 실제 독자(모델, 단계, 호스트), 도구 호출 확인 결과, 판정, 찾은 것의 수(암묵지, 맥락, 오해)와 처리, 답안 시험 결과(맞음, 틀림, 문서에 없음), 글자 수 변화, AS-IS → TO-BE 대표 5개, 사용자에게 물어야 할 사실, 남은 것. 내 글이 아니면 판을 따로 만들고 원문 파일을 덮어쓰지 않는다.
