# sol-loop

코드 변경은 다른 회사 모델 1인과 예산 안에서 합의할 때까지 다듬는다. 예산, 심각도 정의, 반박할 권한은 한 세트다. 리뷰 규칙(읽기 전용, 판 고정, 원장)은 `~/dev/fstack/skills/council/SKILL.md`를 따르고, 아래가 우선한다.

## 리뷰어
- GPT Sol 최신 1인(`~/dev/fstack/local/routing.md` 1절 `reviewer`의 Codex 쪽). 사용자가 버전을 말하면 그 버전이다. ID를 적지 않고 `orchestrator_capabilities`로 확인한다.
- 작성자가 Sol이면 같은 모델끼리 보는 검토가 된다. `reviewer` 규칙의 다른 회사 모델로 돌리고 보고 첫 줄에 적는다. 사용자가 Sol을 다시 지정하면 따른다.
- Sol을 부를 경로가 없으면 다른 모델로 바꾸지 않고 막힌 이유를 보고한다. 리뷰어는 하위 에이전트·다른 리뷰어를 띄우지 않는다.

## 예산
- 기본 3라운드. 1라운드는 전체를 보고, 이후 라운드는 바뀐 코드와 열린 지적만 본다.
- 5라운드까지 늘리는 경우: 보안·권한·인증·데이터 손실·상태·동시성 문제의 blocker·should가 근거와 함께 열려 있거나, 사용자가 요청할 때.
- nit만 남으면 일찍 끝낸다. 거절한 nit, 주석·문서·서식만 고친 것은 새 라운드가 필요 없다.
- 합의 뒤 QA·감시 단계에서 동작 코드를 고치면, 고칠 때마다 고친 부분만 보는 재리뷰 1라운드를 예산 밖으로 더 한다(이 세션에서 최대 2회). 그래도 승인이 나지 않거나 상한을 넘으면 머지 게이트가 거짓이 되고 질문 조건으로 간다.

## 1. 범위
- `git status --short`. 관계없는 변경을 stash·폐기·포함하지 않는다. 변경 경로가 깔끔히 나뉘면 그 경로로 좁히고, 안 나뉘면 멈추고 묻는다.
- `git fetch origin` 뒤 기준 커밋을 정한다. PR이면 `gh pr view <n> --json baseRefName,headRefOid`로 HEAD가 PR head(또는 이번 변경만큼 앞섬)인지 확인하고 `git merge-base HEAD origin/<baseRefName>`. 로컬이면 `git merge-base HEAD origin/<기본 브랜치>`. 원격이 없으면 사용자가 말한 기준, 미커밋 변경만이면 `HEAD`.
- 변경 = 기준부터 작업 트리까지(추적하지 않는 파일 포함). diff 명령 하나를 모든 라운드에 같이 쓴다. 의도 한두 문장과 범위 밖 한 문장을 적는다.
- 변경을 덮는 검사를 돌린다. 이번 변경이 깨뜨린 코드는 보내지 않는다. 없거나 원래 실패하던 검사는 지시서에 적는다.

## 2. 라운드
- T3에서는 라운드마다 새 `delegate_task`(`role: "review"`, `mode: "async"`, 새 `clientRequestId`). 이전 리뷰 스레드에 이어서 묻지 않는다. T3 밖에서는 그 하네스의 Sol 실행 경로 하나를 쓰고 ID를 남긴다.
- 리뷰가 도는 동안 범위 안 파일을 고치지 않는다. 완료 알림을 기다리고 폴링하지 않는다. 타임아웃·오류·무응답은 승인이 아니다.
- 1라운드 지시서(자식은 대화 이력이 없다):

```text
리뷰만 한다. 파일 수정·커밋·푸시·PR 댓글·하위 에이전트 실행을 하지 않는다.
저장소: <절대 경로> 기준: <sha> 의도: <의도> 범위 밖: <범위> 검사: <결과>
볼 것: git diff <base> [-- <경로>]; git status --short(추적하지 않는 파일도 읽는다).
주변 코드를 읽는다. 버그, 깨지는 호출부, 의도와 다른 동작을 찾는다. 버그를 숨기지 않는 한 스타일은 보지 않는다.
가장 작은 변경을 기준으로 의도에 필요 없는 코드·테스트·보호 장치를 짚는다. 다른 경로·드문 경우·작은 성능·추가 호환은 nit이다.
blocker = 의도한 경우가 틀림. should = 의도 안에서 호출부가 실제로 겪을 버그. nit = 나머지.
답 형식(한국어):
VERDICT: APPROVE 또는 CHANGES
S1 [blocker|should|nit] <파일>:<줄> <주장>. Fix: <제안>   (ID는 라운드가 바뀌어도 유지)
```

- 다음 라운드는 예산이 남았고, blocker·should가 열려 있거나 동작 코드가 바뀌었거나 승인이 지금 diff를 덮지 않을 때만 연다. 1라운드 지시서, 원장(`fixed:` / `disagree:` / `declined:` + 근거), 같은 기준 diff, 지난 라운드 이후 바뀐 부분을 보낸다. 이전 ID마다 `resolved` 또는 `still open: <이유>`, 그리고 새 문제만 요구한다.

## 3. 지적에 답하기
- 지적과 심각도를 직접 확인한다. 다른 경로·드문 경우·작은 비용은 붙은 이름과 관계없이 nit이다.
- 동의: 가장 작은 수정. 새 잠금·캐시·도우미·옵션보다 지우거나 좁히는 수정을 고른다. 실제로 일어난 경우를 고친다. 의도에 필요하면 수정 없이는 실패하는 테스트 하나를 더한다.
- 반대: 근거(파일:줄, 테스트, 출력)로 이유를 적는다. 범위 밖·nit: 한 줄로 거절하고 후속 목록에 둔다.
- 원장을 갱신하고 검사와 `git diff --shortstat <base>`를 다시 돌린다. 리뷰가 diff를 키웠으면 먼저 줄인다. 루프를 끝내려고 동의하지 않는다.

## 4. 끝내기
- **합의**: 지금 동작 diff에 APPROVE, 열린 blocker·should 없음, 내 우려 없음.
- **교착**: 같은 지적이 두 번 주고받은 뒤에도 갈리거나 예산이 끝남. 양쪽 입장을 2~3줄씩 보이고 사용자가 정한다. 예산 소진은 승인이 아니다.
- 루프 중에는 푸시하지 않는다. 합의 뒤 푸시는 사용자가 푸시·PR 갱신·`ship` 단계를 승인했을 때만 한다. PR에 올리면 하네스 attribution 줄 위에 한 줄을 넣는다: `Reviewed with sol-loop: <N> rounds with <model>. <실제 리뷰어> verdict: approved` (effort는 확인했을 때만 `on <effort>`).
