# walk

사람의 결정 시간을 아끼는 순서로 넘긴다. 확인할 수 있는 것은 먼저 확인하고, 사람이 정할 것만 한 건씩 선택지와 추천을 붙여 묻는다.

## 모드

| 신호 | 모드 |
|---|---|
| "이슈 확인해줘", "내가 체크할 것만", "하나씩 브리핑" | `issues` |
| "킥오프", "오늘 뭐 해야 돼?", 하루 시작 | `kickoff` |
| "항목 리뷰", 정책·설계 문서의 결정 안건, "다음", "보류" | `decide` |

## issues

1. **읽기**: 열린 이슈 전부(`gh issue list`), 라벨·우선순위(P0~P3)·마감·최근 댓글. 저장소가 여럿이면 저장소별로 묶는다.
2. **에이전트가 끝낼 수 있는 확인부터**: 배포 여부, 재현 여부, 이미 고쳐졌는지는 이 환경에서 가능한 것을 먼저 한다. 여러 개면 `reader`에게 읽기 전용으로 나눠 맡긴다. 결과는 대화에 보고한다. 이슈에 남길 댓글은 초안으로 모아 한 번에 승인받는다(C8, 대리 댓글 표기는 `ship`).
3. **사람 몫만 남기기**: 사람이 결정·실물 확인해야 하는 것만 우선순위 순으로 목록을 만든다. 이미 확인된 것은 개수만 적는다.
4. **한 건씩 브리핑**: 사용자가 "하나씩"을 원하면 한 번에 한 건만 보낸다.

```markdown
**#<번호> <제목>** (P<n>)
- 무슨 일: <한 줄>
- 현황: <확인한 사실, 등급>
- 권고: <추천 처리와 이유>
- 선택: ① <추천> ② <대안>
```

5. **답을 처리로 옮기기**: 보류·닫기·권고대로·새 작업으로 분리를 뜻하는 사용자의 말은 개인 어휘표(`local/core.md`)대로 해석한다. 어휘표에 없는 말이면 보류로 두고 한 줄로 확인한다. 이슈를 닫는 것은 사용자의 이 답이 있을 때만이다.
6. **마무리**: 처리 결과 표(이슈, 처리, 남은 일)와 남은 사람 결정 개수.

## kickoff

1. 서로 결과를 쓰지 않는 조회를 같은 턴에 병렬로 돌린다: 열린 이슈·PR, 어제 야간 자동화 결과(ROUTING의 예약 작업), 기한이 된 **이월 항목**(`verify`·`wrap`이 남긴 것), 사용자가 붙여 넣은 외부 메시지.
2. 한 조회가 실패해도 나머지는 진행하고, 실패를 보고에 남긴다.
3. 기한이 된 이월 항목을 맨 위에 올린다.
4. 질문은 진행에 필요한 것만 그때 묻고, 나머지는 보고 끝에 모아 한 번에 묻는다(C8).
5. 보고는 4줄: 어제 끝난 것 / 오늘 할 것(추천 순서) / 사람 확인 필요 / 막힌 것. 사용자가 고르면 이슈별로 작업을 나눈다(직접 조종할 일은 별도 스레드 제안, C17).

## decide

정책·설계 문서처럼 결정 안건이 여러 개일 때.

1. 안건 하나를 한 줄 요약과 용어 풀이로 제시한다(C2).
2. 선택지 A/B/C마다 의미와 판단 포인트를 쓰고 추천을 반드시 낸다. "보류"로 끝내지 않는다.
3. 사용자의 답(선택지, 안건 번호와 예·아니오, 보류, 다음, 추천대로)을 받는다. 문서 반영은 명시 승인 뒤에 한다. 결정이 여럿이면 번호로 한 번에 답할 수 있게 묶어 보여 줘도 된다.
4. 보류 항목은 목록에 남긴다. 마지막에 전체 결정끼리 상충하지 않는지 점검한다.

## 무인 실행에서

- 확인 이슈를 만들 때 이슈 1개 = 사람 결정 1개로 쓴다. 선택지 ①②와 영향, 근거 시점, 종료 권한(사람)을 적는다.
- 마감은 출처에 적힌 것만 쓴다. 우선순위 기준은 ROUTING 6절에 적힌 문서를 따른다.
- 같은 이슈에 같은 안내 댓글을 회차마다 반복하지 않는다. 상태가 바뀌었을 때만 댓글을 단다.
