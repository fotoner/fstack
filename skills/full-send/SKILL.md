# full-send

이 호출은 머지된 PR까지의 승인이다. 사용자는 이 스레드를 지켜보지 않는다. 위 description의 말을 사용자가 직접 하지 않았으면 이 권한은 없고, `ship` 승인 사다리를 따른다.

이 스킬은 사용자와 대화하는 부모 스레드만 실행한다. 위임받은 자식이면 커밋·푸시·PR·감시를 하지 않고 구현·증거·결과만 부모에게 돌려준다.

## 허가 (이 호출이 곧 승인이다)
- 브랜치 생성, 커밋, 이 작업 브랜치 푸시, PR 생성, 이 PR의 리뷰 답글(`ship`의 대리 댓글 표기).
- 리베이스 뒤 이 작업 브랜치에 한해 `--force-with-lease` 푸시.
- 아래 머지 게이트를 최신 head에서 통과하면 머지.
- **시험 허가**: 증명과 QA에 필요한 시험 방법(앱·개발 서버 실행, 브라우저 자동화, 시뮬레이터·기기, 컴퓨터 사용, 스크린샷)을 먼저 묻지 않고 쓴다. 저장소 지침의 "먼저 묻기"·"시험은 사용자에게"는 이 작업의 시험에 한해 이 호출이 대신한다. 시험 방법 자체의 규칙(정해진 명령, fixture, 실사용 데이터 보호 H2)은 그대로 따른다. 하네스·시스템 승인 창은 우회하지 않는다.

## 허가 밖 (질문 도구로 묻는다)
- 배포·릴리스·앱 설치(사용자가 이 호출에 함께 말했으면 포함). **머지가 곧 배포인 저장소**(`~/dev/fstack/local/routing.md` 4절 "머지 = 배포", 표에 없으면 기본 브랜치 push로 도는 배포·Pages 작업)에서는 머지도 배포로 본다.
- 운영 데이터 변경·삭제, 다른 브랜치 force push, PR 닫기, PR 밖 외부 발송, 브랜치 보호·하네스 승인 창 우회.
- 개인 소유가 아닌 저장소(routing 4절 소유자 판정. routing이 없거나 판정할 수 없으면 개인 소유가 아니다): 머지는 사람이 한다. `full-stop`처럼 머지 직전에서 멈추고 인계한다.

## 단계
1. **마무리**: 요청 목표를 가장 작은 변경으로 끝낸다. 일어난 경우를 고치고, 일어날 수 있는 모든 경우를 고치지 않는다. 기본 브랜치 위면 브랜치를 먼저 만든다.
2. **증명**: 바꾼 것마다 이 세션에서 직접 얻은 증거를 만든다(아래 "증명").
3. **리뷰**: `sol-loop`. 보안·권한·데이터 손실이면 `council` diff. 이 단계에서는 푸시하지 않는다.
4. **QA**: 화면·런타임·기기·외부 연동 동작이 바뀌었으면 리뷰를 반영한 **최종 diff**로 실제 환경에서 사용자 경로를 돌린다(아래 "QA"). QA를 리뷰 전에 하고 끝내지 않는다(리뷰 반영으로 코드가 바뀐다). 순수 리팩터·문서·시험만 바꿨으면 생략하고 이유를 한 줄 적는다.
5. **커밋·푸시·PR**: 이 작업 파일만 의도별로 커밋한다(`ship` 2·3단계). `git fetch` 뒤 최신 기본 브랜치로 리베이스한다. 충돌 해결에 제품·설계 판단이 필요하면 질문한다. 리베이스로 동작이 바뀌었으면 증명과 QA를 그 범위만 다시 한다. `ship` 5단계 점검 뒤 작업 브랜치를 푸시하고 6단계로 PR을 연다. 본문은 문제, 해결, 검증(단계별로 확인한 것), QA 표, 미검증, 리뷰 루프 한 줄(`sol-loop` 푸터).
6. **감시**: 실패한 검사와 진짜 지적을 고치고 고칠 때마다 다시 증명한다(동작이 바뀌었으면 QA와 리뷰도). 오탐은 이유를 달아 답한다. 감시 방법은 아래 "감시".
7. **머지**: 머지 게이트를 통과하면 저장소가 쓰는 방식으로 머지한다(`gh pr merge --match-head-commit <sha>`, 최근 머지된 PR의 방식). 병합 큐·auto-merge를 쓰는 저장소면 GitHub가 머지됐다고 보고할 때까지 남는다.
8. **보고**: 아래 "보고" 형식.

1단계부터 8단계까지 멈추지 않는다. 검사·봇을 기다리는 중에 감시 없이 턴을 끝내면 다시 깨워 줄 사람이 없어 일이 멈춘다.

## 증명
증명은 이 세션에서 직접 본 증거다(명령 출력, 재현, 스크린샷). 가능한 가장 직접적인 것을 쓴다.
- 원래 실패를 재현하고, 고친 뒤 같은 재현이 통과하는 것을 본다.
- 저장소 CI가 돌리는 검사(타입, lint, 시험)를 돌린다. 원래 실패하던 검사는 구분해 적는다.
- 시험이 없고 저장소에 시험 체계가 있으면, 고치기 전에는 실패하는 시험 하나를 더한다.
- 목 처리한 시험의 녹색은 화면·데이터 동작의 증거가 아니다. 그것은 QA가 맡는다.
- 증명 방법을 찾지 못하면 확신이 없는 것이다. 질문 조건으로 간다. 등급 표기는 `~/dev/fstack/shared/evidence-block.md`.

## QA
절차는 `~/dev/fstack/skills/verify/SKILL.md` 2절(환경 출력 → "조건 → 결과" 시나리오 → 자동 실행 → QA 표)을 따른다. 사용자가 지켜보지 않으므로 아래가 그 절보다 우선한다.
- **사람 손·사람 판정이 필요한 항목은 묻지 않는다.** 로그인·기기 연결·2단계 인증·눈으로 판정할 항목은 바로 미검증으로 분류한다. 사용자가 이 호출에 그 준비를 함께 해 두었다고 말했으면 그대로 쓴다.
- 결함이 나오면 고치고 증명을 그 범위만 다시 한다. 동작 코드가 바뀌었으면 `sol-loop`의 QA 뒤 재리뷰 1라운드를 돈다.
- **미검증은 머지를 막지 않는다.** `verify` 2절 3의 기본 미검증 범위(실기기 전용, 다른 OS, 배포 뒤 동작, 실물 장치), routing 4절이 사람 참여로 정한 경로, 위의 사람 손·판정 항목은 PR 본문의 미검증 목록과 `verify`의 이월 항목으로 남긴다.
- **예외: 이번 변경의 목적인 경로를 어느 환경에서도 직접 확인하지 못했으면** 증명할 수 없는 것이다. 머지하지 않고 질문 조건으로 간다(질문에 확인 방법을 넣는다).

## 감시
- 검사도 리뷰 봇도 없는 저장소면 감시하지 않고 바로 게이트로 간다.
- T3: 지금 있는 검사·댓글을 먼저 처리하고 `watch_pull_request`를 건 뒤 턴을 끝낸다. 깨어남은 소식이지 머지 판정이 아니다. 게이트는 직접 조회한다.
- T3 밖: 검사 대기는 `gh pr checks <n> --watch` 하나로 한다. 이 명령은 검사가 끝나면 종료하고 리뷰·병합 큐 사건은 기다리지 않는다. 리뷰를 기다려야 하는데 받을 수단이 없으면 머지하지 않고 질문 조건으로 간다. 직접 폴링·`sleep` 루프를 만들지 않는다.
- 감시는 머지·인계·질문할 때 `unwatch_pull_request`로 푼다. 병합 큐·auto-merge로 머지를 기다리는 동안에는 풀지 않는다(머지되면 저절로 끝난다).

## 질문
일반 메시지의 질문은 보이지 않고 스레드가 끝난 것처럼 보인다. 그래서 질문은 하네스의 질문 도구로만 한다: Claude `AskUserQuestion`, Codex는 지금 모드에서 쓸 수 있는 것(`request_user_input`, 그 모드에서 막히면 `request_user_input_async`. 비동기 질문이면 답이 올 때까지 그 답에 걸린 작업을 진행하지 않는다). PR 링크, 막힌 이유, 추천을 맨 앞에 둔 선택지를 넣는다.

다음 경우에만 묻는다: 증명할 수 없음(QA 절의 예외 포함), 게이트를 스스로 통과시킬 수 없음, 허가 밖 단계, 결과가 갈리는 모호함, 다른 PR이 이 PR을 대체함. PR을 열 수 있는 상태면 먼저 열고 묻는다(사용자가 돌아와 PR에서 바로 이어 보게). 단, 열린 PR을 자동으로 머지하는 무인 통합 규칙이 있는 저장소(`~/dev/fstack/local/routing.md` 4절, `full-stop`과 같은 판정)에서는 질문이 걸린 동안 PR을 열지 않고 브랜치만 푸시한 뒤 묻는다. PR을 여는 순간 질문이 게이트 없는 머지로 바뀐다. 나머지는 기본값으로 정하고 보고에 적는다. 질문 도구가 없거나 답이 없으면 PR을 열린 채 두고 머지하지 않으며 마지막 응답 첫 줄에 질문을 쓴다.
