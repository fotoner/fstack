# 웨이브 구현

병렬 구현의 실패는 대개 코드 품질이 아니라 **작업자끼리 계약을 다르게 해석하거나 같은 파일을 동시에 고치는 데서** 생긴다. 이 스킬은 계약을 먼저 고정하고(W0), 작업자마다 고칠 수 있는 경로를 나누고, 웨이브가 끝날 때마다 오케스트레이터가 직접 합쳐서 검증하는 순서를 정한다.

전제: `council` plan을 마친 구현 계획이 있다(웨이브 표, 소유 경로, 예약 마이그레이션 번호, 웨이브별 통과 기준 포함). 계획이 없거나 blocker가 남아 있으면 구현을 시작하지 않는다.

## 역할 분담

| 역할 | 하는 일 | 하지 않는 일 |
|---|---|---|
| 오케스트레이터(Claude Opus급, ROUTING 2절 계정) | 계획 읽기, W0 작성, 작업자 지시서 작성, 보고 확인, 공유 파일 수정, 통합 점검, 검증 실행, D1 판정 | 웨이브 안에서 작업자 담당 경로의 코드를 대신 쓰기 |
| 작업자(Claude Sonnet 하위 에이전트) | 자기 소유 경로 구현과 테스트, 보고 | 공유 파일 수정, 의존성 추가, 커밋, 비밀값 기록, 유료 API 호출 |
| 점검 작업자(읽기 전용, 필요하면 Codex) | 모듈 사이 계약 불일치 찾기 | 코드 수정 |

- 작업자는 사용자가 따로 지시하지 않으면 Sonnet으로 한다(`Agent`에 `model: sonnet`, T3 위임이면 공급자 목록에서 Sonnet 확인).
- 여러 Claude 계정(ROUTING 2절)과 Codex에 작업을 골고루 배정한다. 한 계정이 한도에 가까워지면 웨이브 폭을 줄이고 다른 계정으로 옮긴다. 배정은 오케스트레이터가 지시서에 적는다.
- 계획·통합·검증은 오케스트레이터가 직접 한다. "작업자가 통과했다고 보고했다"를 완료 근거로 쓰지 않는다.

## 1. W0: 계약 고정 (오케스트레이터)

작업자를 하나라도 띄우기 전에 W0를 끝내고 검증한다. W0 이후에는 아래 "읽기 전용" 경로가 오케스트레이터 전용이다.

W0에 넣을 것:

1. 저장소 초기화, 의존성 설치와 **잠금 파일 고정**. 이후 작업자는 의존성을 추가하지 못한다. 필요하면 요청 사항으로 올린다.
2. 타입 설정, 테스트 설정. 테스트는 **루프백 외 네트워크 접속을 예외로 막는다**(오프라인 검증의 기본).
3. 공용 코어(시간, DB, 로그와 비밀값 마스킹, HTTP 래퍼, 점유·트랜잭션 도우미)와 **계약**(타입, 스키마, 전이표, 모듈 인터페이스, 의존성 묶음).
4. 모든 모듈의 **스텁**: 계획의 시그니처와 같은 이름·인자·반환 타입을 갖추고 몸체는 `throw new NotImplementedError('<모듈>.<함수>')`. 생성 함수는 같은 형태의 객체를 돌려주되 메서드가 던진다. 작업자는 몸체를 채우고 구현한 함수에서 `NotImplementedError`를 없앤다.
5. **기반 마이그레이션**(`0001_init.sql`): 전체 테이블, 제약, 트리거. 이후 작업자는 이 파일을 고치지 않고 자기 예약 번호의 새 마이그레이션만 만든다.
6. 진입점 골격(실행 모드, 루프 등록, 기동 거부 조건)과 환경 변수 예시 파일(비밀 칸은 빈 채로).
7. 계약 예시 fixture(예: `fixtures/contract-chain/`): 단계 사이에 흐르는 데이터의 실제 예시. 모든 작업자가 자기 모듈의 입출력 스키마를 이 예시가 통과하는지 테스트한다.
8. `AGENTS.md`(`templates/AGENTS.md` 참고). 모든 작업자가 가장 먼저 읽는 파일이다. 명령표, 공통 규칙, 읽기 전용 경로, 모듈 소유권 표, 예약 마이그레이션 번호, 프로젝트 불변식(트랜잭션 규칙, 시각 규칙, 비밀값 규칙 등)을 담는다.

W0 통과 기준(계획에 적은 것을 그대로 실행한다. 예):

- 잠금 파일대로 설치가 재현된다.
- 타입 검사와 테스트 통과.
- 마이그레이션 테스트(제약과 트리거가 위반을 거부한다).
- 계약 예시가 스키마를 통과한다.
- 네트워크 차단 장치가 실제로 차단한다는 테스트.
- 진입점이 기동하고 종료한다. 라이브 모드에서 금지된 설정은 기동을 거부한다.

W0를 커밋할 수 있는지는 사용자 허락에 달려 있다(4절). 허락이 없으면 스냅샷으로 되돌릴 지점을 남긴다.

## 2. 병렬 웨이브

### 작업자 지시서

작업자마다 `templates/worker-brief.md`를 채워서 준다. 반드시 들어갈 것:

- 가장 먼저 읽을 파일: `AGENTS.md`, 계획의 해당 절.
- **소유 경로**(고칠 수 있는 곳)와 **읽기 전용 경로**(고칠 수 없는 곳).
- **예약 마이그레이션 번호**(예: W1-A는 0002, W1-B는 0003). 테이블이 더 필요하면 이 번호로 새 파일을 만든다. 남의 테이블은 바꾸지 말고 요청 사항으로 적는다.
- 채울 스텁 목록과 통과 기준(계획의 웨이브별 통과 기준 표에서 가져온다).
- 금지: 의존성 추가, 커밋, 비밀값 기록, 유료 API 호출, 공유 파일 수정, 다른 모듈의 인터페이스 시그니처 변경.
- 시그니처를 바꿔야 하면 구현을 바꾸지 말고 보고의 "요청 사항"에 적는다.
- 보고 형식(`templates/worker-report.md`).

### 소유 규칙

- 작업자 사이에 겹치는 경로는 없어야 한다. 겹치면 웨이브 구성을 다시 짠다.
- 읽기 전용 경로(공유 파일)는 오케스트레이터만 고친다: 계약, 코어, 기반 마이그레이션, 의존성·잠금 파일, 타입·테스트 설정, 공용 테스트 도우미, 모델 설정, `AGENTS.md`, 폰트 등 자산 원본.
- 한 작업자가 예외로 고칠 수 있는 공유 파일이 있으면(예: 마지막 조립 작업자의 `package.json` scripts) 지시서에 줄 단위로 적는다.
- 같은 웨이브의 작업자는 서로의 소유 경로 결과물을 기다리지 않는다. 의존이 생기면 W0의 스텁과 계약을 기준으로 개발하고 통합은 웨이브 사이에서 한다.
- 웨이브 안에서는 계약을 바꾸지 않는다. 바꿀 필요가 생기면 오케스트레이터가 모아 두었다가 **다음 웨이브 전에** 반영한다.

### 웨이브 구성 원칙

- 먼저 다른 모듈에 의존받는 바닥 모듈(수집, LLM, 렌더, 게시)을 병렬로 돌린다.
- 이들을 조합하는 모듈(파이프라인, 승인·알림)을 다음 웨이브에 둔다.
- 사용자 화면과 조립·e2e·배포 문서는 마지막 웨이브에 둔다.
- 웨이브당 작업자 수는 2~4명을 권장한다. 한 번에 많이 띄워도 통합 점검 비용이 커진다.

## 3. 웨이브 사이 통합 점검 (오케스트레이터)

웨이브마다 모든 작업자 보고를 받은 뒤 순서대로 수행한다(`templates/integration-checklist.md`).

1. **보고 확인과 요청 사항 반영.** 보고에 적힌 변경 파일이 소유 경로 안에 있는지 확인한다(`git status` 또는 스냅샷 비교). 경로 밖을 건드렸으면 되돌리고 이유를 작업자 보고에 따라 판단한다. 요청 사항(시그니처, 환경 변수, 마이그레이션)은 오케스트레이터만 공유 파일에 반영한다.
2. **마이그레이션 점검.** 빈 DB에서 전체 적용과, **이전 웨이브 시점 DB에서의 업그레이드** 둘 다 확인한다. 번호 충돌, 순서, 체크섬 오류가 없어야 한다.
3. **타입 검사, 전체 테스트, 진입점 기동 확인**을 직접 실행한다. 작업자가 자기 테스트만 돌렸을 가능성을 전제로 한다.
4. **계약 불일치 점검.** 구현이 쌓이면 읽기 전용 점검 작업자(다른 회사 모델 권장)에게 맡긴다: 모듈들이 서로 호출하는 지점에서 인자, 상태 이름, 이벤트 이름, 에러 분류, 소유권이 계약과 일치하는지 대조하고, 불일치를 파일·줄·기대값·실제값으로 보고하게 한다. 수정은 하지 않는다.
5. **정본 결정.** 점검에서 두 모듈이 서로 다르게 구현한 것은 오케스트레이터가 하나로 정하고 `AGENTS.md` 끝 절("통합 점검에서 정한 정본")에 한 줄씩 남긴다. 다음 웨이브 작업자가 그 규칙을 따른다.
6. **작업 트리 스냅샷.** 커밋하지 않는 상태라면 `node_modules` 등을 제외하고 `/tmp`에 압축한다(`tar --exclude=node_modules --exclude=.git -czf /tmp/<프로젝트>-<웨이브>.tgz .`). 되돌릴 지점이다. 사용자의 작업 트리를 `stash`, `reset`, `checkout`으로 바꾸지 않는다.
7. **통과 기준 대조.** 계획의 웨이브별 통과 기준 표의 항목마다 어떤 명령으로 확인했는지 기록한다. 실행하지 못한 항목은 숨기지 않고 "미검증"으로 적는다.

통과하지 못하면 다음 웨이브를 시작하지 않는다. 실패한 작업자에게는 실패 명령과 출력, 기대값을 담은 수정 지시서를 보낸다. 같은 작업자에게 두 번 실패하면 범위를 줄이거나 오케스트레이터가 직접 고친다.

## 4. worktree로 병렬 브랜치 나누기

기본은 **같은 작업 트리**에서 소유 경로로만 나누는 방식이다. 작업자가 많거나 서로의 중간 상태(깨진 빌드)가 방해될 때는 worktree를 쓴다. worktree는 브랜치를 만들고 커밋이 필요하므로 **사용자가 커밋을 허락했을 때만** 쓴다.

| 상황 | 방식 |
|---|---|
| 커밋 허락 없음, 작업자 2~3명 | 같은 작업 트리 + 소유 경로 + 웨이브 사이 스냅샷 |
| 커밋 허락 있음, 작업자 4명 이상이거나 서로의 깨진 빌드가 방해됨 | worktree 브랜치 |

절차:

1. W0를 커밋한 기준 커밋을 확인한다. 사용자의 현재 작업 트리에 미커밋 변경이 있으면 건드리지 말고 먼저 묻는다.
2. 작업자마다 브랜치와 worktree를 만든다.
   ```bash
   git worktree add ../<프로젝트>-w1-a -b wave/w1-a <W0 커밋>
   git worktree add ../<프로젝트>-w1-b -b wave/w1-b <W0 커밋>
   ```
3. 각 worktree에서 `pnpm install --frozen-lockfile`처럼 잠금 파일대로 의존성을 설치한다(`node_modules`는 worktree마다 필요하다).
4. 지시서에 **worktree의 절대 경로**를 적고, 그 밖의 경로를 읽기 전용으로 둔다. 작업 시작 보고에 `git -C <경로> status`와 현재 브랜치를 적게 해서 올바른 곳에서 일하는지 확인한다.
5. 작업자는 자기 소유 경로만 수정하고, 커밋은 사용자가 허락한 방식(작업자가 자기 브랜치에 커밋 / 오케스트레이터가 커밋)으로 한다. 지시서에 명시한다.
6. 웨이브가 끝나면 오케스트레이터가 통합 브랜치(`wave/w1-integration`)에서 브랜치를 하나씩 병합한다. 소유 경로가 겹치지 않으므로 충돌은 예약 마이그레이션 번호, 공유 파일 변경 요청, 배럴(`index.ts`)에서만 나와야 한다. 다른 곳에서 충돌이 나면 소유 규칙 위반이므로 원인을 먼저 찾는다.
7. 병합 뒤 3절의 통합 점검을 **통합 브랜치에서** 실행한다. 통과하면 다음 웨이브의 worktree를 통합 브랜치의 새 커밋에서 만든다.
8. 끝난 worktree는 `git worktree remove`로 지운다. 지우기 전에 해당 브랜치가 병합되었는지 확인하고, 미병합 변경이 있으면 지우지 않고 보고한다.
9. 사용자의 `main`에는 직접 병합하지 않는다. 최종 결과는 통합 브랜치로 남기고 사용자가 병합을 승인한다. push와 PR 생성은 사용자 허락 뒤에 한다.

## 5. 마지막 웨이브와 D1 판정

마지막 웨이브(조립, e2e, 배포 문서, 라이브 확인 스크립트)가 끝나면 오케스트레이터가 **직접** 계획의 D1 항목을 하나씩 실행한다.

1. 타입 검사 오류 0.
2. 전체 테스트 통과, 테스트 중 루프백 외 네트워크 접속 0.
3. e2e 통과. 실제 진입점을 오프라인 모드로 띄워 전체 흐름을 보는 e2e와, 복구 경로(강제 종료 후 재기동)를 따로 본다.
4. 눈으로 확인해야 하는 산출물(렌더 이미지, 화면)은 파일을 열어서 직접 본다. 자동 검사 통과는 근거가 되지 않는다.
5. 저장소에 비밀값이 없다(검사 스크립트와 정규식 훑기). 환경 변수 예시 파일이 모든 변수를 설명한다.
6. 진입점 기동을 일정 시간(예: 3분) 유지하며 오류 로그가 없는지 본다.

판정 규칙:

- D1은 "외부 계정 없이 확인할 수 있는 범위의 구현 완료"다. D1 통과를 D2나 D3로 표현하지 않는다. README에 단계 표(D1·D2·D3와 상태)를 둔다.
- 라이브 호출(실제 API, 실제 사이트)을 하지 않았으면 그렇게 쓴다.
- 실행하지 못한 검증은 최종 보고에 "미검증"으로 남긴다. 일부 항목이 실패하면 D1 미달이다.
- 판정 보고는 `templates/d1-report.md`를 쓴다. 각 항목에 명령, 시각, 결과를 적는다.
- 커밋과 푸시는 사용자 허락 뒤에만 한다. 커밋 단위는 의도, 위험, 검증 게이트 기준으로 나눈다.

## 하지 말아야 할 것

- 계약이 흔들리는 상태에서 작업자를 띄우지 않는다.
- 작업자 보고의 "통과"를 직접 실행 없이 완료로 기록하지 않는다.
- 공유 파일을 작업자에게 풀어 주지 않는다. 예외가 필요하면 줄 단위로 허용한다.
- 의존성 추가를 작업자 판단에 맡기지 않는다.
- 사용자의 미커밋 변경을 stash, reset, checkout으로 옮기지 않는다. `git add .`, `git add -A` 같은 넓은 staging을 쓰지 않는다.
- 비밀값을 채팅으로 받지 않는다. 파일이나 `request_secret`을 쓴다.
