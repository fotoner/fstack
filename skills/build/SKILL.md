# build

구현은 재현에서 시작해 증거로 끝난다. 공유 자원은 먼저 선언하고, 작성자와 검증자는 나누고, 같은 원인은 전수로 고친다.

## 모드 고르기

| 신호 | 모드 |
|---|---|
| 버그 하나, 작은 기능, 파일 몇 개 | `light` |
| 이슈 여러 개, "이슈별로", "워커에 맡겨", 이어받은 오케스트레이션 | `issue` |
| `council`을 거친 계획서가 있고, 모듈 계약을 병렬로 나눠야 함 | `wave` |

## 공통 규칙

- 시작할 때 한 줄 복창과 이번 작업 제약(C6): 목표, 하지 않을 것, 예상 최소 변경, 대상 저장소·브랜치, 승인 범위(예: "dev PR까지, 머지·배포 제외"). 작업 위치(worktree 여부)는 `~/dev/fstack/local/routing.md` 4절 저장소별 규칙을 따른다.
- 모델과 effort는 ROUTING 1절: 작업자 `worker`, 어려운 것만 `worker-hard`(이유를 적는다), 리뷰는 작성자와 다른 모델. 풀리지 않으면 ROUTING 1절의 단계 순서(`worker-hard` → `council` → `advisor`)로 한 단계씩 올린다. 동시 상한을 지킨다.
- **다치는 길(H1·H2)을 지킨다.** 실제 사용자 데이터 대신 fixture·임시 사본을 쓰고, 시험의 기본 경로를 임시 폴더로 둔다. 시험 환경(환경 변수, 시험 활성 조건)을 바꾸는 변경은 그 자체를 검토 대상으로 본다: 새로 켜지는 시험이 무엇에 쓰는지 먼저 확인한다.
- 작업자의 "완료"는 `[보고]`다(C15). diff와 검사 결과를 직접 보고, 개수는 직접 센다.
- 지적받은 문제는 승인된 기능·저장소 안에서 같은 원인을 찾아 함께 고치고, 범위 밖 발견은 보고만 한다.
- 끝은 `verify`의 증거 블록이다. 커밋·푸시·PR은 `ship`이 맡는다.

## light

1. 버그면 실패를 먼저 재현한다. 증거 종류는 버그 유형으로 정한다:
   - 논리·상태 버그: 고치기 전에 실패하는 시험을 먼저 만든다.
   - 화면 버그: 실제 앱에서 재현하고 전후 캡처를 남긴다(캡처는 UI가 바뀐 곳에만).
   - 서버 전용: 시험 + 실제 요청·로그 기록.
   재현을 못 하면 그 사실과 시도한 경로를 적고, 추측 수정을 완료로 보고하지 않는다.
2. 가장 작은 변경으로 고친다. 증상 대신 처음 잘못된 지점을 고친다. 주변 코드를 정리하지 않는다.
3. 같은 재현으로 통과를 확인하고, 저장소의 관련 검사만 돌린다(예: `check.sh --changed`). 전체 검사는 저장소 규칙이 정한 때(릴리스 등)에 한다.
4. 승인된 범위 안에서 같은 원인을 찾아 "수정 / 해당 없음" 표를 만든다.
5. UI·런타임 동작은 앱을 실제로 띄워 본다. 모킹된 시험 통과는 사용자 경험의 증거가 아니다.
6. UI를 바꿨으면 화면 문구를 점검한다(C22): 이번 변경에서 새로 넣은 설명 문장·툴팁·안내 문구만 센다(기본 0, 오류·빈 상태 문구와 아이콘 버튼의 접근성 이름은 세지 않는다). 개수와 이유는 코드 주석이 아니라 작업 보고에 적는다. 새로 넣은 것 중 라벨을 되풀이하거나 여러 화면에 반복되는 것은 지운다. 기존 문구는 요청이 없으면 목록으로만 보고한다.

## issue

1. 열린 이슈·PR을 훑어 이미 해결된 것부터 거른다. 처리할 이슈마다 브랜치·작업 위치(ROUTING 4절 저장소 규칙. 예: 이슈 1개 = 세션 1개 = worktree 1개)·**소유 경로**·**공유 파일 목록**을 정한다. 겹치면 순서를 정하거나 한 작업자에게 묶는다.
2. **조율과 구현을 나눈다.** 사용자가 "조율만"을 말했거나 이슈가 셋 이상이면 오케스트레이터는 구현하지 않는다. 사용자가 각 이슈를 직접 보고 조종하고 싶어 하면 서브에이전트 대신 이슈별 별도 스레드와 핸드오프 문서로 나누자고 제안한다(C17).
3. 동시 작업자 수와 각자의 모델·effort를 첫 보고에 적는다. 무거운 작업(전체 검사, 빌드, 오디오·GUI 사용)은 한 번에 하나만 돌게 잠금을 둔다. 상한을 못 채우면 이유를 알린다.
4. 작업자 지시서는 `~/dev/fstack/shared/delegate-brief.md` + `templates/worker-brief.md`: 이슈, 브랜치·작업 위치 절대 경로, 소유 경로, 읽기 전용 경로, 공유 파일 규칙, 검증 명령, 금지(의존성 추가·커밋·라이브 자원·남의 PID), 업무에 필요한 예외(예: 사용자가 승인한 이슈 댓글), 보고 형식(한국어, 바꾼 것 / 확인한 것: 명령과 수치 / 남은 것).
5. 구현 작업자와 **읽기 전용 리뷰 작업자**를 분리한다. 리뷰는 작성자와 다른 모델이 하고, 구현 맥락 없이 코드를 받는다. 지적 ID를 원장에 남긴다. 같은 계열 지적이 두 번 나오면 그 이슈만 고치지 말고 검사나 체크리스트로 올린다(`lesson`).
6. 병합 순서를 먼저 정하고 그 순서로 충돌을 푼다. 승인 범위 밖(main 병합, 릴리스, 배포)은 하지 않는다.
7. 상태판을 유지한다(C5): 이슈, 작업자, 진행, 막힘, 사용자가 할 것. 한 작업에는 세션 하나만 둔다. 재개하기 전에 같은 작업을 잡은 세션이 없는지 본다.
8. 끝: 이슈마다 남길 검사 수치 댓글을 초안으로 모아 한 번에 승인받는다(무인 실행이나 지시서에 명시된 예외는 바로). 닫기는 승인 범위 안에서. 병합한 worktree·브랜치·세션을 정리한다. 정리까지가 완료다. 이어받을 일이 있으면 `wrap`의 핸드오프를 쓴다.

## wave

검토를 마친 계획서가 있을 때만 쓴다. 계획이 없거나 작으면 `issue`나 `light`로 충분하다.

1. **W0(오케스트레이터 직접)**: 계약·스텁·마이그레이션 번호 예약·`AGENTS.md`(소유 경로 표)·의존성 고정. W0이 통과해야 작업자를 띄운다.
2. **W1…**: 소유 경로가 나뉜 `worker`를 병렬로. 지시서 `templates/worker-brief.md`, 보고 `templates/worker-report.md`.
3. **웨이브 사이 통합 점검**: 타입·시험·기동·계약 불일치·소유 경로 위반(`templates/integration-checklist.md`).
4. **D1 판정**: 직접 실행한 검증으로만(`templates/d1-report.md`). D1은 오프라인 구현 완료이며 D2(라이브)와 섞어 보고하지 않는다.

세부 절차는 `references/wave.md`를 따른다. 그 문서의 계정·모델 이름은 ROUTING 역할표로 읽는다.
