# council

검토는 작성자와 다른 모델이 읽기 전용으로 한다. 지적은 오케스트레이터가 직접 판정한다. 목표는 지적의 수가 아니라 합의된 작은 결과물이다. 같은 모델로 절차만 두 번 도는 것은 교차 리뷰가 아니다.

## 규칙

1. **검토만 요청받았으면 고치지 않는다.** "리뷰해줘", "Sol로 리뷰해줘"처럼 검토만 요청받았으면 원장과 반영안까지만 돌려준다(C11). 지적을 반영하고 다음 라운드를 도는 것은 내가 작성 중인 산출물이거나 사용자가 수정을 맡겼을 때만이다.
2. **위원은 `~/dev/fstack/local/routing.md`의 `council` 역할(1인이면 `reviewer`)이다.** 사용자가 위원을 지정하면 따른다. 위원을 못 부르면 ROUTING 1절의 대체 순서로만 바꾸고(그 밖의 비슷한 모델로 바꾸지 않는다), 대체 위원과 실제로 돈 위원 수를 점수표에 적는다. 대체 순서까지 못 부르면 보고한다. 같은 모델을 다른 호스트에서 부르는 것은 대체가 아니다.
3. **위원은 읽기 전용이다.** 지시서로 금지하고, 기계로도 확인한다: 위원에게는 고정한 판(보존 사본 경로나 diff 파일)을 주고, 라운드 전후에 대상과 보존본의 `sha256sum` 목록을 비교한다. 바뀌었으면 원인을 확인하고 그 라운드 응답을 버린다. `isolation: "worktree"`는 부모 커밋에서 만든 체크아웃이라 커밋하지 않은 판을 빼므로, 검토 판이 커밋돼 있을 때만 쓴다.
4. **알려진 문제는 먼저 고친다**(수정 권한이 있을 때). 이미 아는 결함을 위원에게 다시 찾게 해서 라운드를 낭비하지 않는다.
5. **범위를 지키는 것은 오케스트레이터의 일이다.** 같은 목표를 더 작게 푸는 수정을 먼저 고르고, 범위 밖 제안은 후속 목록으로 뺀다. 라운드가 결과물을 키웠으면 먼저 줄인다.
6. **지적은 직접 확인한 뒤 받아들인다.** 동의하지 않으면 근거(파일:줄, 실행 결과)로 반박한다. 라운드를 끝내려고 동의하지 않는다. 위원의 권고는 결정이 아니다. 사용자가 정한 방침과 부딪치면 사용자 방침이 이긴다.
7. 다음은 승인이 아니다: 예산 소진, 타임아웃, 오류, 무응답, 판정 없이 점수만 있는 응답.

## 모드

| 모드 | 대상 | 위원 | 보는 축(고정 질문 포함) |
|---|---|---|---|
| `plan` | 계획서·기획서 | 3사 | 요구·계약 공백, 실패 모드, 외부 사실, **기존 운영에 주는 영향**(구버전·호환·배포 순서) |
| `design` | 설계 문서·스킬·운영 규칙 | 3사 | 근거와 맞지 않는 규칙, 규칙끼리 충돌, 실행 불가 절차, 과잉 명세, 기존 운영 영향 |
| `report` | 조사·분석 보고서 | 3사 또는 `reviewer` | 수치의 분자·분모·기간, 근거 없는 단정, 반대 가설 |
| `diff` | 코드 변경 | 3사 또는 `reviewer` | 정확성, 깨지는 호출부, 의도와 불일치, 기존 운영 영향 |
| `visual` | 시안·그림·UI | 3사 또는 `reviewer` | 레퍼런스와 다른 형태, 빠진 요소, 화면 문구, 설명·장식 과잉(C22) |
| `solo` | 계획·문서·시안을 1인에게 | `reviewer` 1인 | 대상에 맞는 위 축. 코드 diff를 Sol 1인과 반복하는 것은 `sol-loop` |

- 큰 대상은 **관점 분리**(위원마다 다른 축)나 **조각 분할**(diff를 영역별로)로 보낼 수 있다. 위원끼리 판정이 갈린 지적은 다음 라운드에 그 지적만 다른 위원에게 맡긴다.
- 예산은 기본 3라운드다. 사용자가 횟수를 말하면 그 수다. 보안·권한·데이터 손실·동시성 blocker·should가 근거와 함께 열려 있으면 최대 2라운드를 더하고 이유를 적는다. nit만 남으면 일찍 끝낸다.
- 내가 쓴 큰 계획서(`plan`)는 사용자에게 보이기 전에 `solo` 1라운드를 기본으로 거친다. 사용자가 빼라고 하면 뺀다. 보고서와 작은 초안은 요청할 때만.

## 절차

### 0. 준비
- 대상 판을 고정한다. 문서는 판을 보존하고(`r0` 사본), diff는 기준 커밋(`git merge-base`)과 diff 명령 하나를 모든 라운드에 같이 쓴다.
- 의도 한 줄, 범위 밖 한 줄, 이미 돌린 검사와 결과, 사용자가 정한 방침을 적는다.

### 1. 위원 확인
- `orchestrator_capabilities`로 각 위원의 provider·model·effort를 확인한다. ID를 스킬에 적지 않는다.
- 원격 위원에게는 대상 전문을 넣거나, 크면 `~/dev/fstack/local/routing.md` 3절의 파일 전달 경로로 보내고, 받는 쪽에서 sha256을 대조하게 한다.

### 2. 위임 (라운드마다 새로)
- 위원마다 새 `delegate_task`: `role: "review"`, `mode: "async"`, 라운드별 새 `clientRequestId`, 모델과 effort는 `target.providerInstanceId`·`target.model`·`target.options`. 이전 라운드 위원 스레드에 `t3_thread_send`로 이어서 묻지 않는다.
- 지시서는 `templates/review-brief.md`. 심각도 정의, 점수(N/10), 응답 형식, 이전 라운드 원장을 넣는다.
- 위원이 판 안의 파이썬을 돌리게 하려면 `python3 -I -B`로 쓰게 한다(`-I`는 환경변수를 무시해 `PYTHONDONTWRITEBYTECODE`가 먹지 않는다. 캐시 파일이 판을 바꾼다).
- 위원이 도는 동안 대상을 고치지 않는다. 완료 알림을 기다린다. 폴링하지 않는다.
- T3가 아닌 하네스에서는 그 하네스의 다른 회사 모델 실행 경로를 쓰고 기록한다. 경로가 없으면 보고한다.

### 3. 원장과 반영표
- 위원 응답은 기록 위치(`~/dev/fstack/local/routing.md` 6절)에 `r<N>-<위원>.md`로 원문 그대로 보존한다.
- 지적마다 원장 한 줄: ID, 위원, 심각도(위원 → 내 판정), 합의도(몇 위원이 짚었나), 처리(반영 / 바꿔서 반영 / 반박 / 범위 밖), 근거. 형식은 `templates/response-table.md`.
- 다른 경로·드문 경우·작은 비용은 위원이 뭐라고 붙였든 nit이다.
- 반영은 가장 작은 수정이다. 지우거나 좁히는 수정을 새 장치보다 먼저 고른다.

### 4. 개정판과 다음 라운드 (수정 권한이 있을 때)
- 직전 판을 보존하고 새 판을 만든다.
- 남은 예산이 있고 blocker·should가 열려 있거나 동작이 바뀌었으면 다음 라운드를 연다. 지시서에 이전 원장과 바뀐 부분을 넣고, 위원에게 이전 ID마다 해소 / 미해소(이유)와 새 문제만 요구한다.
- 마지막 라운드까지 합의하지 못한 blocker가 남았으면 ROUTING 1절의 `advisor`에게 대상 판, 원장, 위원별 입장, 남은 선택지를 넘겨 의견을 받는다. `advisor`의 의견도 결정이 아니다. 판정과 사용자에게 물을 것은 오케스트레이터가 정한다.

### 5. 종료와 보고
- 합의: 위원 모두 승인(또는 nit만 남음)하고 내가 아는 문제가 없다.
- 교착: 같은 지적이 두 번 오간 뒤에도 남거나 예산이 끝났다. 양쪽 주장을 2~3줄씩 적고 사용자가 정한다.
- 보고 맨 앞에 점수표를 둔다. 점수가 없으면 `no score`로 쓰고 지어내지 않는다. PR이 있으면 PR 본문에 넣는다(댓글 아님).

```markdown
## 컨실 결과
라운드: 3 · 위원: 3/3

| 위원 | r1 | r2 | r3 |
|---|---|---|---|
| Claude Opus | 6/10 | 7/10 | 8/10 |
| GPT Sol | 5/10 | 7/10 | 8/10 |
| Gemini | 7/10 | no score | 9/10 |
```

## 하지 않는 것
- 위원이 쓴 원문을 고쳐 쓰지 않는다.
- 같은 라운드에 같은 위원을 두 번 부르지 않는다.
- 위원의 점수나 승인을 추측해 채우지 않는다.
