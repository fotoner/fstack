# ship

git 쓰기는 사용자가 말한 단계까지만 한다. 말한 단계는 끝까지 한다. 모든 git 쓰기 보고는 단계 현황표로 끝낸다.

## 승인 사다리

`커밋` < `푸시` < `PR` < `머지` < `배포`

- 사용자가 말한 단계까지만 한다. "PR 올려줘"는 머지를 포함하지 않는다. 짧은 진행 승인은 직전에 제안한 단계까지다. "브랜치만 만들어"는 커밋 승인이 아니다.
- **호출 = 승인**: 사용자가 단계를 말하며 부르면("머지 직전까지 ㄱ", "PR까지 ㄱ") 그 아래 단계는 모두 승인된 것이다. 첫 보고 줄에 허용 목록과 금지 목록을 적는다. 예: `허용: 브랜치·커밋·작업 브랜치 푸시·PR / 금지: 머지·기본 브랜치 push·배포·외부 발송`.
- "커밋하고 쭉 진행"이면 커밋 단위 승인 질문을 생략하고 의도별로 나눠 커밋한 뒤 해시·제목만 보고한다. 푸시·머지·배포·외부 반영은 여전히 명시 승인이다.
- 머지는 명시 승인이나 ROUTING 5절의 예외에서만 온다. 스킬이 스스로 권한을 만들지 않는다. 배포는 기본적으로 사용자가 한다.
- 다음은 머지와 같다고 보고 금지한다: auto-merge 켜기, merge queue 넣기, 기본 브랜치에 직접 push, 브랜치 보호 우회(`--admin`), 이 일을 다른 에이전트에 위임.
- 사용자가 "full send"·"full stop"·"머지 직전까지 맡길게"처럼 끝까지 맡기면 `full-send`·`full-stop`으로 간다. 그 호출이 그 범위의 승인이다. 단계만 말한 요청("PR까지 ㄱ")은 이 스킬의 사다리다.

## 절차

1. **위치**: `~/dev/fstack/local/routing.md` 4절 저장소별 규칙을 따른다(표에 없으면 기존 체크아웃에서 브랜치). 사용자의 미커밋 변경이 있으면 stash·reset하지 않는다. 그 변경과 섞이면 worktree를 첫 선택지로 묻는다. 기본 브랜치 위면 브랜치를 먼저 만든다.
2. **범위 점검**: `git status --short`. 이 작업과 관계없는 변경은 커밋에서 뺀다. 넓은 staging(`git add -A`, `git add .`)을 쓰지 않고 파일을 지정한다. diff 규모와 생성물 비율을 요청 범위와 대조한다.
3. **관례**: 브랜치 이름·커밋 메시지·PR 제목은 최근 이력(`git log --oneline -20`, 최근 브랜치)의 관례를 따른다. 여러 저장소를 한 번에 커밋하지 않는다.
4. **검사**: 저장소의 관련 검사(ROUTING 4절의 검사 명령)와 `verify` 증거 블록. 커밋 단위는 의도·위험·검증 단위다.
5. **비밀값·공개 글 점검**: push 전에 diff·커밋 메시지·PR 본문에서 비밀값 패턴·개인 경로·계정 ID를 훑는다(C19). 공개 저장소에 쓰는 글에서 `@`는 실제로 부를 사람에게만 쓴다(`@이름` 형태의 표기는 백틱 안에 둔다).
6. **PR 열기**: 이미 이 브랜치의 PR이 있는지 먼저 본다. 본문은 **문제부터** 쓴다(무엇이 불편했고 이제 어떻게 되는지). 변경 목록으로 시작하지 않는다. 검증 한 줄(증거 등급), 리뷰를 했으면 결과(컨실 점수표나 리뷰어·라운드), 하네스가 정한 attribution 줄을 넣는다. 드래프트가 아닌 일반 PR로 연다.
7. **연결·감시**: T3에서는 `link_pull_request`로 스레드에 연결한다. 감시는 사용자가 요청했거나 `full-send`·`full-stop`으로 맡았을 때만 `watch_pull_request`로 한다. 직접 폴링·`sleep` 루프를 만들지 않는다. 위임받은 자식은 PR을 감시하지 않는다. 손을 뗄 때는 `unwatch_pull_request`를 먼저 부른다.
8. **리뷰 지적**: 시점과 관계없이 아직 처리되지 않은 지적 전체를 현재 head와 대조한다. 소스와 대조한 뒤 고치거나, 동의하지 않으면 "고치지 않음 + 이유" 답변 초안을 만든다(게시는 C8·대리 댓글 규칙). 리뷰 루프가 PR을 키우면 줄인다. 리베이스한 브랜치는 `--force-with-lease`로만 푸시한다.
9. **머지 게이트(머지 권한이 있을 때만)**: 본문에 적은 조건이 아니라 조회한 조건으로 판정한다. `git fetch`한 최신 head에서 모두 참이어야 한다.
   - 증거(`verify`)가 diff 전체를 덮는다. 화면·런타임 동작이 바뀌었으면 최종 diff의 QA에서 변경 목적인 경로는 직접 확인해 통과했고, 나머지 바뀐 경로는 통과했거나 미검증(사람 손·판정, 실기기 전용, 다른 OS, 배포 뒤 동작)으로 PR 본문과 이월 항목에 있으며, 실패는 없다(`verify` 2절, `full-send` QA 절).
   - PR에 붙은 검사가 모두 끝났고 성공이다(`gh pr checks <n>`, 건너뜀·중립 포함). 검사가 0개면 0개라고 보고한다. 브랜치 보호의 필수 검사가 없는 저장소가 많아서 "필수만"으로 보지 않는다.
   - 최종 head를 덮는 리뷰의 마지막 판정이 승인(APPROVE)이거나 nit만 남았다. 리뷰 뒤 동작을 바꿨으면 그 변경을 다시 리뷰받는다. 리뷰를 못 했으면 거짓이다.
   - 봇·사람의 지적은 고쳤거나 이유를 적어 답했다. 변경을 요청한 사람 리뷰가 남아 있지 않다.
   - 기본 브랜치를 포함한다(`git merge-base --is-ancestor origin/<base> <head>`)고 GitHub가 머지 가능하다고 보고한다.
   - **머지 권한 조건**: 머지가 배포를 일으키지 않거나(routing 4절 "머지 = 배포"), 배포 승인이 있다. 원격 소유자가 개인 소유다(routing 4절. routing이 없거나 소유자를 판정할 수 없으면 개인 소유가 아니다). 아니면 머지하지 않고 사람에게 넘긴다.
   - 병합은 검토한 SHA에 고정한다(`gh pr merge --match-head-commit <sha>`). 하나라도 거짓이면 머지하지 않고 이유를 보고한다.
10. **미루는 결함**: 리뷰에서 나온 결함을 머지 뒤로 미루면 PR 본문의 "이월 목록"에 쓰고 각각 이슈(심각도 포함)로 만든다. 보안·노출·데이터 손실 결함은 미루지 않는다. P1 이월 이슈가 열려 있으면 릴리스·태그를 만들지 않는다.
11. **정리**: 머지 후 이번 작업의 worktree·로컬 브랜치를 정리한다(원격 브랜치는 저장소 관례대로).

## 끝까지 맡길 때 (`full-send` · `full-stop`)

사용자가 "full send"·"full stop"을 말하면 그 스킬이 절차(증명·QA·리뷰·PR·감시·게이트)를 갖는다. 그 절차가 이 스킬의 5·6단계(공개 글 점검, PR 열기), 8단계(리뷰 지적), 9단계(머지 게이트)를 부른다.

## 단계 현황표 (git 쓰기를 한 보고의 끝)

짧은 확인("푸시했어?")에는 한 줄로 답하고 표를 붙이지 않는다.

```markdown
| 단계 | 상태 | 근거 |
|---|---|---|
| 구현 | 반영 [코드] | <커밋 sha> |
| 검사 | 통과 | <명령·결과> |
| 리뷰 | sol 1라운드 승인 / 안 함 | |
| QA·실물 확인 | 미확인 | 이월: <항목·기한> |
| 커밋·푸시 | 완료 / 안 함(범위 밖) | |
| PR | <URL> / 안 함 | |
| 머지·배포·공유 | 사용자 몫 | |

대신 정한 것: <브랜치 이름, 커밋 분할 기준 등>
```

## 무인 실행(예약 작업·야간 자동화)

- 질문 도구에 답할 사람이 없다. 막히면 PR을 열린 채 두고 머지하지 않으며, 막힌 이유를 PR 본문이나 확인 이슈에 남긴다. 미응답은 "머지하지 않음"이다.
- 저장소 자체의 무인 통합 규칙이 있는 저장소(ROUTING 4·5절에 적힌 것만)는 그 규칙을 따른다. 그 저장소에서 머지를 막으려면 PR을 열지 않고 브랜치만 푸시한다. 다른 저장소에는 그 예외를 적용하지 않는다.

## 되돌리기

머지된 변경을 되돌려야 하면: 무엇이 검증되지 않았는지 먼저 쓰고, PR마다 revert 커밋 하나로 나누고(하나씩 다시 올릴 수 있게), 원래 PR에 다시 올릴 조건을 댓글로 남긴다. 되돌리기 PR도 이 스킬의 승인 사다리를 따른다.

## 대리 댓글 표기

사용자 계정으로 GitHub에 댓글·리뷰 답글을 남길 때 맨 앞에 붙인다.

```markdown
> [!NOTE]
> 🤖 **<모델 이름>이 <사용자 GitHub 로그인> 대신 답함**
```

결론부터 쓰고, 근거(코드·검사·재현)를 붙이고, 확인한 사실과 판단을 나눈다. 게시 전에 비밀값을 훑고, 게시 후 URL이 돌아왔는지 확인한다. PR 본문·커밋 메시지·사용자가 그대로 올리라고 한 글에는 붙이지 않는다.
