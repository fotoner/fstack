# ops

운영 점검은 읽기 전용이다. 모든 숫자에는 무엇을 셌는지 붙인다. 실패와 빈 응답은 성공으로 지나가지 않게 드러낸다.

## 점검 모드

1. **변경 금지 선언**: 배포, 삭제, 설정 변경, 코드 수정, 운영 데이터 쓰기, 비용이 드는 로그 tail을 하지 않는다고 첫 줄에 적는다. 토큰은 읽기 권한만 쓴다(C11).
2. **순서**: 헬스체크(실제 요청 1회) → 배포 상태(서비스 중인 커밋 vs main, `~/dev/fstack/shared/evidence-block.md`) → 지표·로그. 독립 실패가 있어도 나머지 점검은 계속한다. 점검 호스트 자신의 네트워크 문제를 서비스 장애로 오판하지 않게 자가 점검을 먼저 한다.
3. **숫자 규칙(C14)**: 숫자마다 무엇을 셌는지(요청·세션·사용자), 기간, 표본 여부(샘플링 보정), 사람·봇·내부 트래픽 구분 기준을 붙인다. 경계값 근처는 원본 행과 대조한다.
4. **가설이 여럿이면**: 가설마다 `reader`를 하나씩 읽기 전용으로 띄운다(`~/dev/fstack/shared/delegate-brief.md`). 반증된 가설은 메모리·노트에 남겨 다시 조사하지 않는다.
5. **의심 해소형 질문**("수상한데", "봇 아니야?")은 `research`의 의심 해소 기준을 먼저 적는다.
6. **결과**: 결론 한 줄(정상 / 이상 / 판단 불가), 근거, 이상이면 이슈 후보와 우선순위(P0~P3). 고치는 일은 별도 작업과 승인으로 넘긴다.

## 모니터링 모드 (배포 뒤)

1. 간격과 끝나는 시각을 정한다. 사용자가 말한 값("10분 간격, 9시까지", "3시간 간격, 24시간")을 그대로 쓰고, 없으면 묻지 않고 "30분 간격, 3시간"으로 시작해 보고에 적는다.
2. 볼 지표와 경보 기준(오류율, 특정 오류 신규 발생, 응답 시간)을 한 줄로 적는다.
3. 예약(`schedule_task`)이나 하네스의 반복 실행으로 돌린다. 직접 `sleep` 루프를 만들지 않는다.
4. 변화가 있을 때만 보고한다. 끝나는 시각에 종합 한 번을 보고하고 예약을 지운다.

## 예약 모드

T3 예약 작업을 만들거나 고칠 때.

1. **주기와 겹침**: 시각·주기를 정하고 같은 호스트의 다른 예약 작업(`list_scheduled_tasks`)과 겹치는지 본다. 정각 경합(pull과 머지 같은)을 피한다.
2. **얇은 부모**: 예약 스레드의 부모는 직접 점검하지 않고 지정 모델 자식에게 위임만 한다. 모델은 사용자가 정한 것, 없으면 ROUTING 1절의 `triage`·`reader`. 자식이 실패하면 부모가 대신하지 않고 실패를 보고한다.
3. **지시서**: 읽기 전용 범위, 변경 금지 목록, 판정 기준표(정상·경고·장애), 무인 규칙(질문하지 않고 기본값으로 진행, 한 항목이 실패해도 나머지 진행, 커밋·푸시·PR 금지, 마지막에 "확인 필요" 요약), 보고 형식(이상 없음은 한 줄), 이슈 규칙(장애면 생성, 복구면 같은 이슈에 댓글, 같은 상태로 댓글을 반복하지 않음, 닫기는 사람). 비밀값(웹훅 URL 등)은 출력·저장하지 않는다.
4. **실패를 성공으로 보지 않는다**: 인증 오류, 한도, 빈 응답, 0바이트 결과, 자식 미실행은 장애로 판정하고 보이는 곳(이슈·보고)에 남긴다.
5. **첫 실행 확인**: 첫 예약 실행 시각을 적고, 그 실행의 결과를 직접 본다(다음 턴이나 확인 예약). `run_scheduled_task_now` 즉시 시험은 사용자가 요청·승인했을 때만 한다("예약만 해줘"는 실행하지 않는다). 첫 실행을 보기 전에는 "등록 완료"라고만 쓰고 "동작함"이라고 쓰지 않는다.
6. **문서화**: 주기·모델·범위·이슈 규칙을 저장소 README나 운영 문서에 반영한다(커밋은 `ship`).
