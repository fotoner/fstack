# verify

완료는 조회와 재현으로만 말한다. 증거 등급 없이 "됐다"고 하지 않는다. 사용자가 다시 확인할 것을 먼저 확인한다.

## 규칙

- 증거 등급은 `[실물]` > `[합성]` > `[코드]` > `[보고]`다(C15). 실행·배포·화면·기기 효과를 주장하는데 `[실물]`이 없으면 "완료" 대신 "합성 통과", "코드 반영"처럼 등급 그대로 쓴다. 문서·설정 편집 자체는 "반영함 [코드]"로 충분하다.
- 단계마다 본 것과 못 본 것을 나눈다: 코드 검사 → 화면 → 데이터 수신 → 반영·배포.
- 상태는 추측하지 않고 조회한다(`~/dev/fstack/shared/evidence-block.md`의 명령표). 증거는 지금 head의 정확한 트리에서 모은 것이어야 한다. 커밋이 바뀌면 다시 본다.
- 사용자가 다음에 할 조작을 그대로 재현한다: 새 로그인 셸, 실제 브라우저 화면, 모바일 폭, 실기기, 라이브 URL, 렌더한 영상·소리.
- 결과 확인을 사용자에게 미루지 않는다. 지금 보거나, 나중에 볼 예약을 걸고 시각을 적는다(C5).
- 이 호스트에서 실물 확인이 불가능하면 ROUTING 3절 호스트 표에서 가능한 호스트·역할을 찾는다(포커스가 필요한 GUI는 `ui-checker`). 그래도 안 되면 사람 확인 항목으로 넘긴다(C10).
- 중단된 검증(한도·타임아웃·인증 오류)은 통과가 아니다.

## 1. 완료 판정 (모든 작업)

1. 요청 항목마다 무엇을 확인해야 "됐다"인지 한 줄로 적는다. 항목이 여럿이면 항목별 충족표를 만든다. 사용자가 한 곳을 지적했으면 승인된 기능·저장소 안에서 같은 원인을 찾아 "수정 / 해당 없음"으로 함께 보고하고, 범위 밖 발견은 보고만 한다.
2. 항목마다 가장 높은 등급의 확인을 한다. 화면은 스크린샷을 직접 열어 정렬·잘림·한글 깨짐을 보고, 소리·영상은 렌더 후 구간별로 확인한다.
3. 증거 블록을 채운다. 커밋·푸시·PR·머지·배포 상태 줄은 조회 결과로 채운다.
4. 못 한 확인은 **이월 항목**으로 넘긴다: 무엇을, 어떻게 확인하면 통과인지, 실패하면 무엇을 할지, 기한. 대화형이면 보고에, 무인 실행이면 확인 이슈로 올린다(`walk`). 다음 킥오프에서 기한이 된 것을 맨 위에 올린다.

## 2. QA (기기·시뮬레이터·브라우저)

"QA 진행해줘"와 `full-send`·`full-stop`의 QA 단계가 이 절을 쓴다. 순서는 환경 → 시나리오 → 사람 손 한 번에 → 자동 실행 → 사람 판정 묶음 → 보고다. 사용자가 "다음"을 반복해 넘기는 진행을 없애는 것이 목적이다.

1. **환경을 먼저 출력한다**: 호스트, 빌드 종류와 커밋(최종 diff인지), API 환경(dev/stage/prod), 계정, 기기·OS·브라우저, 띄울 포트. 사용자가 지정한 환경·도구는 끝까지 유지한다. prod에서는 저장·발송·데이터 변경 동작을 하지 않는다.
2. **시나리오**: 체크리스트가 있으면 쓰고, 없으면 바뀐 사용자 경로마다 만든다.
   - 모든 항목은 "조건 → 결과"다. 결과 칸에 무엇이 보이면 통과이고 무엇이 보이면 실패인지 적는다("~ 확인"처럼 판정 기준이 없는 항목은 쓰지 않는다).
   - 기대값은 현재 코드가 정본이다. 옛 시험 계획을 베끼지 않고, 그 상태를 지금 환경에서 실제로 만들 수 있는지 본다. 실행 전제가 다른 항목은 따로 묶는다.
   - 실행자가 결함으로 오인할 만한 정상 동작은 따로 적는다.
   - 체크리스트는 저장소에 저장하지 않고 보고와 PR 본문에만 둔다(사용자가 저장을 요청하면 예외).
3. **범위**: 저장소 규칙(`~/dev/fstack/local/routing.md` 4절)이 우선하고, 없으면 아래 기본값을 쓴다. 실기기와 다른 OS는 사용자가 요청하지 않으면 시도하지 않고 미검증으로 둔다.

   | 유형 | 직접 확인 | 기본적으로 미검증 |
   |---|---|---|
   | 모바일 앱 | 시뮬레이터의 기존 개발 빌드 | 실기기 전용 경로, 다른 OS, 분석 이벤트 실수신, 원격 업데이트 반영 |
   | 웹 | 로컬 개발 서버와 브라우저 조작 | 운영 데이터가 있어야 보이는 화면 |
   | 백엔드 | 시험·e2e, 필요하면 로컬 서버에 실제 요청 | 배포 뒤 동작 |
   | 데스크톱 앱 | 로컬 빌드 실행과 화면 조작(포커스가 필요하면 `ui-checker`) | 실물 장치·실사용 데이터가 필요한 경로(3절) |
   | 그 밖 | 저장소가 정한 시험·빌드 | 저장소 밖 반영 |

4. **사람 손이 필요한 일은 시작 전에 한 번에** 요청한다(로그인, 기기 연결, 원격 디버깅 허용, 2단계 인증). 에이전트가 할 수 있는 것(시뮬레이터 실행, 앱 재시작, 테스트 계정 로그인)은 직접 한다.
5. **환경 함정**:
   - 기존 개발 빌드가 이번 변경을 반영할 수 있으면(예: 번들러가 다시 읽는 코드만 바뀜) 그 빌드를 쓴다. 네이티브 코드·빌드에 묶이는 리소스·설정이 바뀌었으면 다시 빌드한다. 어느 쪽인지 QA 표의 환경 줄에 적는다.
   - 다른 작업자가 쓰는 기본 포트를 피해 별도 포트로 띄운다. 띄운 PID만 끈다(H1).
   - 앱 변형(운영·개발)의 식별자를 먼저 확인한다. 다른 변형의 주소를 쓰면 운영 앱이 열린다.
   - 운영 원격 업데이트와 운영 데이터가 끼어들지 않게 막는다. 여러 세션이 함께 쓰는 개발 계정에서는 설정을 저장하지 않는다.
   - 백그라운드 임시 서버(번들러, 미리보기)는 수명 제한이 있다. 제한과 재기동 명령을 함께 준비한다.
6. **자동 실행**: 조작할 수 있는 항목은 직접 한다(앱은 기기 조작 도구, 웹은 브라우저 도구). 항목마다 통과·실패와 증거(스크린샷 경로, 로그, 조회 결과)를 남긴다. 잠깐 떴다 사라지는 표시는 캡처 대신 상태·로그로 기록한다.
7. **사람이 판정할 항목은 묶어서** 한 번에 보여 주고 결과를 받는다. 하나씩 넘기지 않는다.
8. **결함**: 재현 절차, 기대 결과, 실제 결과, 증거를 적는다. 고치는 것은 사용자가 요청했거나 `full-send`·`full-stop` 흐름일 때만이다.
9. **보고**: QA 표(항목 / 환경 / 결과 / 증거)와 미검증 목록(무엇을, 어떻게 확인하면 통과인지). 나중에 확인할 것은 1절 4단계의 이월 항목으로 남긴다. 직접 보지 않은 항목을 통과로 쓰지 않는다.

## 3. 사람 참여 실험 (실물 장치·실데이터)

에이전트가 할 수 없는 실물 조작(USB 꽂기, 하드웨어 버튼, 앱 화면 편집)이 필요할 때.

1. 먼저 에이전트가 할 수 있는 준비(사본 백업, 측정 스크립트, 대조 기준)를 다 한다.
2. 사용자 단계를 번호로 준다: 무엇을, 어떤 파일(실제 파일 이름·앨범·위치), 무엇을 누르고, 얼마나 기다리는지. "할까요?"로 묻지 않는다.
3. 실데이터를 쓰면 실제라고 먼저 밝히고, 끝나면 기준 사본으로 되돌린다.
4. 사용자가 "완", "끝", "꽂음"이라고 하면 바로 결과를 분석하고 다음 단계를 준다.

## 4. 판정기·분류기 검증

LLM 판정기, 분류기, 집계 파이프라인처럼 정답이 있는 것을 만들 때.

1. 합성 데이터·고정 사례와 의도한 판정(정답지)을 한 정의 파일에서 만든다.
2. 실행 끝에 "의도 대 실제" 비교표를 출력하게 한다.
3. 실데이터는 읽기 전용 쿼리로만 가져오고, 쿼리를 기록하고, 저장소 밖에 둔다.

## 5. 배포 판정 (D1·D2·D3)

| 단계 | 뜻 | 증거 |
|---|---|---|
| D1 | 오프라인 구현 완료 | 직접 실행한 시험·빌드·기동 |
| D2 | 라이브 관측을 시작할 수 있음 | 실제 계정·실환경에서 smoke, 격리 부정 시험, 비밀값 배치 확인 |
| D3 | 관측 종료 | 정해진 기간의 운영 지표 |

- 단계를 섞어 보고하지 않는다. "D1 통과, D2 미착수"처럼 쓴다.
- 배포는 기본적으로 사용자가 한다(ROUTING 5절). 사용자가 이 작업에서 배포를 맡겼을 때만 배포 단계를 실행한다.
- 사람이 동석해야 하는 단계와 외부에 남는 영향(공개 URL, 웹훅, DNS)을 시작 전에 한 번에 알린다.
- 증거 문서 `templates/d2-evidence.md`, 부정 시험 `templates/negative-tests.md`, smoke 스크립트 `templates/smoke-script-contract.md`. 대상별 절차(systemd, Tailscale Serve, Cloudflare Tunnel, 비밀값 배치)는 `references/deploy.md`. Cloudflare Pages/Workers는 `wrangler deployments list`와 라이브 응답의 버전 표식, Docker Compose는 `docker compose ps`·healthcheck·재기동 후 볼륨 유지·외부 요청 1회로 본다.
