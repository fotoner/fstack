# fstack 설계

## 1. 실패 분류 (F1~F19)

fstack의 규칙과 스킬은 아래 실패를 막기 위해 있다.

## 2. 원칙

1. **CORE가 스킬보다 먼저다.** 스킬을 부르지 않는 대화의 실패는 항상 실리는 계약으로 막는다. CORE는 개인 보충과 합쳐 9,000B를 넘지 않는다. 옮긴 규칙 번호는 다시 쓰지 않는다.
2. **CORE는 실린 것을 확인한다.** 계정 폴더별 사용자 지침과 Codex 지침에 관리 블록으로 복사하고, 설치 뒤 저장소 밖 새 세션에서 실렸는지 묻는다.
3. **스킬은 적게, 트리거는 사용자의 말로.** 쓰이지 않는 스킬은 지운다. description에는 목적어가 붙은 구절만 둔다. 자주 부르는 이름은 다른 스킬의 모드로 합치지 않는다.
4. **개인 값은 `local/`에만 둔다.** 스킬은 ROUTING의 역할 이름만 부르고 모델 ID를 쓰지 않는다. 개인 맥락은 공개 저장소에 두지 않는다.
5. **권한은 사용자의 말과 정본 파일에서만 온다.** 평소에는 말한 단계까지만 간다. "full send"·"full stop"은 그 범위의 승인이다. 개인 소유가 아닌 저장소에서는 머지 직전에서 멈춘다. 마지막 단계에서 멈춘 일은 단계 현황표로 드러낸다.
6. **게이트는 문장이 아니라 조회다.** 머지는 조회한 조건(검사 결과, 리뷰 판정, 검토한 SHA)으로 판정한다. 반복되는 교정은 훅과 검사로 옮긴다. fstack 자체도 `check_fstack.py`로 검사한다.
7. **QA는 리뷰 뒤 최종 diff로 한다.** 리뷰 반영으로 코드가 바뀐다. 무인 실행의 미검증은 이월하고 머지를 막지 않는다. 변경 목적인 경로를 확인하지 못하면 머지하지 않는다.
8. **리뷰는 규모에 비례하고, 단계를 올린다.** `worker` → `worker-hard` → `council` → `advisor`. 위원은 ROUTING의 대체 순서로만 바꾼다. 위원과 조언자의 권고는 결정이 아니다.
9. **금지는 실제로 다치는 길에만 둔다(H1~H4).** 이름·패턴 kill, 실사용 데이터 쓰기, 대화 중인 서버 재시작, 섞인 폴더 삭제.
10. **교정의 효과는 재발 횟수로 잰다.** 재발한 규칙은 강제 수단을 한 단계 올린다(구조 > 스킬 절차 > 규칙 > 문서 > 메모리).

## 3. 워크플로 → 스킬

| 흐름 | 스킬 |
|---|---|
| 조사 → 기획 → 적대적 검증 → 웨이브 구현 → 확인 → 배포 | `research` → `council` plan → `build` wave → `verify` → `ship` |
| 이슈 → 이슈별 worktree 작업자 → 독립 리뷰 → 병합 → 정리 | `walk` → `build` issue → `sol-loop` → `ship` → `wrap` |
| 끝까지 무인 진행(증명·리뷰·최종 diff QA·PR·감시·머지) | `full-send` / `full-stop`(머지 게이트는 `ship`) |
| 단발 조사·링크 요약 | `research` light |
| 환경 셋업·장애 진단·기기 정리 | `setup` |
| 이슈 워크스루, 아침 킥오프, 결정 안건 루프 | `walk` |
| 서비스 운영 점검·예약 트리아지·배포 후 모니터링 | `ops` |
| 실물 실험, 시뮬레이터·브라우저·실기기 QA | `verify` |
| 핸드오프·이어받기 | `wrap` |
| 저장소를 에이전트용으로 구성·축소 | `harness` |
| 반복 교정을 규칙·검사로 | `lesson` |
